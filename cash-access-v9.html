THE CUSTOMER PROBLEM

The till is closed.
The day isn’t quite done.

A practical journey for a café owner with cash to pay in.

THE MOMENT

“My usual branch is closed.”

The café owner has finished trading, counted the takings, and is ready to go home. They need somewhere suitable to deposit the cash.

A list of nearby branches leaves the important questions unanswered: which locations advertise a deposit facility, what hours are published, and what access information is missing?

“Help me find an option I can check before I make the journey.”
THE EXPERIENCE

One task. Clear evidence.

  1. Tell us where you are.A postcode, search radius and planned visit.
  2. Find published deposit facilities.Combine both live feeds instead of assuming every ATM takes cash.
  3. Compare a main option and alternatives.Distance, accessibility, the source evidence and branch schedule.
  4. Check what the data cannot confirm.Call before travelling when machine access or account requirements matter.

What success looks like

The customer can identify a suitable advertised facility and see the remaining checks. The demo does not make deposits, access accounts, guarantee machine availability, or promise that cash will be credited today.

Less search effortMeasure time to find an evidenced option.
Fewer unsupported claimsEvery capability links back to a source field.
More reuseThe same tools serve a website, an assistant and authorized MCP clients.

MCP access architecture

Apigee · asia-south1

Example client entry points. Connect each client to the MCP endpoint with its own authorized demo key.

Three tools, multiple uses

  • find_cash_deposit_optionsCafé owner planning a cash deposit.
  • find_nearby_atmsCustomer looking for a withdrawal location.
  • find_nearby_branchesCustomer looking for a branch or Local site.

Stateless MCP over HTTP is implemented inside the proxy. This demo does not use Google's managed MCP Discovery proxy.

Where the controls apply

  • Before the toolsReject unknown fields, invalid locations, dates, tool names and unauthorized clients.
  • At the MCP boundaryModel Armor screens tool inputs and returned evidence. Each client keeps its own conversation context.
  • Before showing resultsReturn source-backed evidence and keep unknowns explicit.
